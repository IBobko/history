# Публикация todo100.ru через GitHub Actions

Основная ветка: `main` репозитория `IBobko/history`.

| Workflow | Когда запускается | Что публикует |
| --- | --- | --- |
| Publish archive content | Изменены `Russia/`, `USA/`, `Common/` | Снимок всех годовых Markdown-файлов; приложение продолжает работать |
| Deploy archive application | Изменён `web/` | Проверенный Docker-образ и содержимое архива из того же коммита |

Правки самих workflow также запускают соответствующие проверки. В pull request
выполняются проверки без доступа к публикации. Изменения только `docs/` или
`tools/` не запускают публикацию. Новое событие по-прежнему добавляется только
через `tools/timeline.py`; Actions переносит готовые файлы без редактирования.

Если один push меняет и архив, и `web/`, workflow содержимого выполняет проверки,
а публикацию поручает workflow приложения. Обе операции имеют отдельные очереди
GitHub и общую блокировку `/run/lock/project-deploy/history.lock` на сервере.
Они не могут переключать версии одновременно. Устаревший запуск, SHA которого
уже не совпадает с актуальным `main`, отклоняется; повторить запуск нужно для
последнего коммита `main`.

## Обычная работа

1. Изменить материалы или код и проверить diff.
2. Сделать коммит и `git push origin main`.
3. Открыть [Actions репозитория](https://github.com/IBobko/history/actions).
4. Дождаться зелёного результата и проверить [сайт](https://todo100.ru).

Изменения локальных файлов до commit и push на сайт не попадают.

Для ручного запуска выбрать workflow → **Run workflow** → ветку `main`.
Параметр `check_only` по умолчанию включён: проверяются тесты, доступ и работающий
сайт, опубликованная версия не заменяется. Для публикации снять этот флажок.
Ручная публикация содержимого публикует полный снимок, включая удаления файлов.

## Проверки и переключение версий

Оба workflow устанавливают зависимости по lock-файлу, проверяют импортер и весь
архив. Неизвестные даты, пустые блоки, потерянный вводный текст и дубли идентичности
блокируют публикацию. Расхождение даты с именем годового файла остаётся явно
выведенным предупреждением. Старое оформление само по себе не считается ошибкой.

Workflow приложения дополнительно проверяет откат помощника, собирает Next.js
и проверяет TypeScript. Затем сервер получает **тот же SHA** из фиксированного
публичного GitHub-репозитория и собирает Docker-образ. Образ не передаётся через
SSH и не требует доступа к registry. Временный контейнер без внешней сети
проверяет чтение нового архива до публикации.

Снимки хранятся в `/opt/history-archive/content/releases/<SHA>/`.
Единственная ссылка `content/current` переключается атомарно. Приложение разрешает
её в конкретный путь перед чтением файлов, поэтому один запрос читает один снимок.
При правках только текста рабочий контейнер не пересоздаётся.

Образы имеют тег `history-archive:<SHA>`. Помощник обновляет только строку образа
в защищённом Compose и ждёт готовности контейнера. Затем проверяет локальные
`/api/health` и главную страницу, а workflow — публичный HTTPS через российский
прокси. Перезапуск приложения может вызвать короткий перерыв в ответах.

Если локальная проверка после переключения не проходит, помощник возвращает
предыдущую ссылку и прежний образ, проверяет восстановление и завершает workflow
ошибкой. Сбой внешнего прокси отмечается ошибкой workflow после локальной
публикации; автоматический откат из-за внешнего прокси не выполняется.

Сохраняются пять последних снимков и образов, а также активная и непосредственно
предыдущая версия образа. Старые образы удаляются только из `history-archive`;
глобальный Docker prune не используется. Сборочный кеш очищает администратор
при необходимости. Снимки на этом сервере не заменяют внешнюю резервную копию.

## Доступ и установка помощника

Используется `deploy@91.99.238.7` и существующий секрет `DEPLOY_SSH_KEY`.
Приватный ключ не попадает в репозиторий. Ключ сервера закреплён в `publish.sh`.
Workflow имеет только `contents: read`; сервер читает публичный репозиторий
по HTTPS без отдельного GitHub-токена.

Администратор через личный YubiKey устанавливает:

- `history-deploy.py` → `/usr/local/sbin/history-deploy`, `root:root`, `0755`;
- `sudoers-history-deploy` → `/etc/sudoers.d/history-deploy`, `root:root`, `0440`;
- `history.compose.yml` → `/etc/project-deploy/history.compose.yml`, `root:root`, `0644`.

Каталоги `/opt/history-archive`, `content`, `content/releases` и checkout
`repository` контролируются root. На первом запуске администратор сохраняет
работающий архив в `content/releases/bootstrap`, создаёт `current` и переводит
контейнер на единственное подключение `content` из защищённого Compose.
Исходные папки первого размещения сохраняются как начальная резервная копия.

Команды `sudo -n /usr/local/sbin/history-deploy check|content|code` разрешены
только с одним из трёх точных аргументов. Для публикации полный SHA подаётся
через stdin. Произвольные пути, команды, Compose-файлы и registry не принимаются.
Правки помощника, sudo и защищённого Compose в Git **не устанавливаются
автоматически**: их отдельно проверяет и устанавливает администратор.

У `deploy` нет общего sudo, доступа к Docker-сокету и права менять защищённую
конфигурацию. Общий ключ деплоя не предоставляет доступ к root. Общий помощник
других проектов `/usr/local/sbin/project-deploy` остаётся отдельным.

Текущее состояние публикации: `/etc/project-deploy/history-state.json`.
В нём записаны SHA материалов и кода, время и предыдущая версия.
